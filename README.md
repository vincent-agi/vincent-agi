## How I approach software

- **Simple first.** The best architecture is the one the next developer understands without me in the room.
- **Boundaries over frameworks.** Domain, use cases, infrastructure — frameworks are details plugged at the edges (Clean Architecture, SOLID).
- **Tests are a design tool.** If something is hard to test, it is usually badly cut.
- **Write decisions down.** ADRs, runbooks, READMEs that explain *why* — code alone never does.
- **Learn by reasoning.** When I teach, I explain the trade-off before the syntax.
